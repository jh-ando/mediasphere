> 팀원들과 **코드를 같이 열어 놓고** 읽기 위한 문서입니다. 기능마다 ① 무엇을 하는지 ② 흐름 ③ 실제 코드(발췌)와 해설 ④ 왜 이렇게 했는지(겪은 문제) ⑤ 같이 이야기해 볼 것 순서로 정리했습니다.

## 0. 읽는 법

### 0.1 추천 세션 구성 (1회 약 1시간)

| 회차 | 범위 | 핵심 질문 |
|---|---|---|
| 1 | 1장 전체 그림, 2장 시간, 3장 영상 재생 동기화 | 439대가 어떻게 "같은 순간"을 아는가 |
| 2 | 4장 명령 체계, 5장 패턴, 14장 운영 제어 | 서버 명령이 폰 화면이 되기까지 |
| 3 | 6장 텍스트 스크롤, 7장 텍스트 패턴 | 프레임을 보내지 않고 글자를 흐르게 하는 법 |
| 4 | 8장 영상 분할, 9장 배포, 10장 영상 교체 | 영상 하나가 439개 파일이 되어 폰에 들어가기까지 |
| 5 | 11장 자동 복구, 12장 OTA, 13장 상태 보고 | 현장에 안 가고 439대를 관리하는 법 |

### 0.2 이 시스템을 관통하는 세 가지 생각
1. **서버는 "무엇을, 언제" 한 번만 말하고, 폰이 각자 계산한다.** 영상도 텍스트도 프레임을 실시간으로 보내지 않습니다. 파라미터와 기준 시각만 보냅니다.
2. **"언제"는 항상 서버 시계 기준 절대 시각이다.** 메시지가 폰마다 다른 시각에 도착해도 결과가 같게 하려는 것입니다.
3. **같은 메시지가 두 번 와도, 순서가 바뀌어도, 폰이 꺼졌다 켜져도 결과가 같아야 한다.** MQTT QoS1·retain과 439대 규모에서 이 원칙이 깨질 때마다 버그가 났습니다.

## 2. 시간 — 폰 439대가 서버 시계를 갖는 법

[sync/TimeSyncManager.kt](../../android/app/src/main/java/com/mediasphere/client/sync/TimeSyncManager.kt)

폰 시계는 서로, 그리고 서버와 수십~수백 ms(때로는 몇 달!) 차이가 납니다. 그래서 **"서버 시계로 지금 몇 시인가"**를 폰마다 추정합니다. NTP와 같은 원리입니다.

```kotlin
object TimeSyncManager {
    @Volatile private var offsetMs: Long = 0L
    fun now(): Long = System.currentTimeMillis() + offsetMs   // ← 앱 전체가 시각 비교에 이것만 씀

    private fun measureOffset(serverIp: String): Long? {
        // …
        val t1 = System.currentTimeMillis()                    // 요청 보내기 직전(폰 시계)
        val responseBody = connection.inputStream.bufferedReader().use { it.readText() }
        val t2 = System.currentTimeMillis()                    // 응답 받은 직후(폰 시계)
        val serverMs = JSONObject(responseBody).getLong("serverMs")
        serverMs - (t1 + t2) / 2                               // 서버가 응답을 만든 순간 ≈ 왕복의 한가운데
    }

    suspend fun sync() {  // 5번 재서 중간값 - 한 번 튄 측정(Wi-Fi 지연)에 끌려가지 않게
        // …
        offsetMs = median(offsets)
    }
}
```

**그림으로**
```
폰:   t1 ──────요청──────▶          ◀──────응답────── t2
서버:                     serverMs
offset = serverMs − (t1+t2)/2     (요청·응답 지연이 비슷하다고 가정)
```

**왜 이렇게 했나**
- Phase 1 때 drift가 계속 한쪽으로 치우쳐서 만들었습니다(S3).
- 주기는 처음 1분이었습니다. 텍스트 스크롤이 재동기화 순간마다 튀는 문제가 생겨 5초로 줄이고, 텍스트 쪽에는 완충을 넣었습니다(6장).
- 실제 사례: 시계가 몇 달 틀린 폰 한 대만 텍스트가 앞서 갔습니다(S9). `offset`은 그 차이를 메워야 하는데, 시스템 시계가 갑자기 보정되면(`ACTION_TIME_CHANGED`) 즉시 다시 잽니다.

**같이 이야기해 볼 것**: 5초마다 HTTP 5번 × 439대 = 초당 약 440건. 영상 모드에서도 이 주기가 필요한가? (09 가이드 4.1의 ❓)

### 3.3 폰: PLAY 받기 → 시작 위치 맞추기 — [MainActivity.kt:983](../../android/app/src/main/java/com/mediasphere/client/MainActivity.kt#L983)
```kotlin
// handleControlMessage
is MqttControlMessage.Play -> {
    playbackStarted = false
    pendingPlayJob?.cancel()                        // 새 PLAY가 오면 이전 대기는 버림
    pendingPlayJob = lifecycleScope.launch { scheduleStart(message.startAt) }
}

private suspend fun scheduleStart(startAt: Long) {
    val now = TimeSyncManager.now()
    val delayMs = maxOf(START_DELAY_MS, minOf(startAt - now, 5000L))  // 최소 1초, 최대 5초 대기
    delay(delayMs)
    startPlayback(startAt)
}

private fun startPlayback(startAt: Long) {
    val duration = player.duration
    if (duration > 0) {
        val targetPos = ((TimeSyncManager.now() - startAt) % duration + duration) % duration
        player.seekTo(targetPos)                     // "startAt부터 지금까지 흐른 만큼" 위치로
    } else {
        pendingStartAt = startAt                     // 길이를 아직 모르면 STATE_READY에서 다시
    }
    player.play()
    playbackStarted = true
}
```
**핵심**: 폰마다 메시지 도착 시각이 달라도, 모두 **같은 `startAt`에서 흐른 시간**으로 위치를 계산하므로 같은 장면에서 시작합니다. 1초 대기는 재생 직후 drift가 크게 튀던 문제(S6) 때문에 넣었습니다. 대기 시간은 위치 계산에 이미 반영됩니다.

### 3.4 폰: 재생 중 계속 맞추기 — [sync/DriftCorrector.kt:34](../../android/app/src/main/java/com/mediasphere/client/sync/DriftCorrector.kt#L34)
```kotlin
fun correct(player: Player, elapsedMs: Long, masterMs: Long) {
    val duration = player.duration
    if (duration <= 0) return
    // 패킷이 출발한 뒤 흐른 시간만큼 보정 (전송 지연 보정)
    val adjustedElapsedMs = elapsedMs + (TimeSyncManager.now() - masterMs)
    val targetPos = ((adjustedElapsedMs % duration) + duration) % duration

    // 루프 경계: 목표가 5900→100처럼 반 바퀴 넘게 뛰면 이번 한 번은 건너뜀
    if (lastTargetPos >= 0 && abs(targetPos - lastTargetPos) > duration * LOOP_BOUNDARY_RATIO) { /* … */ return }

    val drift = player.currentPosition - targetPos     // +면 내가 빠름, -면 내가 느림
    when {
        abs(drift) < 16  -> player.playbackParameters = PlaybackParameters(1.0f)   // 정상: 속도 원복
        abs(drift) <= 50 -> applySpeedCorrection(player, drift, 0.015f, …)          // ±1.5%
        abs(drift) <= 100 -> applySpeedCorrection(player, drift, 0.03f, …)          // ±3%
        abs(drift) <= 200 -> applySpeedCorrection(player, drift, 0.05f, …)          // ±5%
        else -> { player.seekTo(targetPos); player.setPlaybackSpeed(1.0f) }         // 너무 멀면 점프
    }
}
```
- **seek는 화면이 끊겨 보이므로** 작은 차이는 속도를 살짝 바꿔 따라잡습니다. 사람 눈에 ±5% 속도 차이는 안 보입니다.
- 16ms ≈ 30fps에서 반 프레임입니다(동기화 목표 < 16ms).

**같이 이야기해 볼 것**
- 구간별 속도(1.5/3/5%)를 비례 제어(drift × 계수)로 바꾸면 어떤 장단점이 있을까?
- UDP 패킷이 잠깐 끊기면 무슨 일이 생기나? (보정만 멈추고 재생은 계속됨)

## 6. 텍스트 스크롤 — 프레임을 보내지 않고 글자를 흐르게 하기

[text/TextScrollView.kt:188 `onDraw`](../../android/app/src/main/java/com/mediasphere/client/text/TextScrollView.kt#L188)

**아이디어**: 439대 전체를 **하나의 거대한 캔버스**로 보고, 그 위에 텍스트를 한 번만 그린다고 상상합니다. 각 폰은 캔버스에서 **자기 자리만큼 잘라서** 보여 줍니다. 서버는 텍스트·폰트·속도·`startAt`만 한 번 방송합니다(`TEXT_SCROLL`).

```
전체 캔버스 (gridWidthPx × gridHeightPx)
┌──────────────────────────────────────────────┐
│        ← ← ←   M e d i a S p h e r e         │  originX = 텍스트 블록의 현재 위치
│   ┌───┐┌───┐┌───┐                             │
│   │폰A││폰B││폰C│  ← 각 폰은 자기 칸(pitch)만 그림 │
└──────────────────────────────────────────────┘
```

### 6.1 한 칸의 크기: 폰 화면이 아니라 "간격 포함" 크기
```kotlin

val pitchH = height / (1.0 - p.gapRatioY).toFloat()
```
폰 사이엔 베젤과 거치대 공간이 있습니다. 이걸 무시하면 글자가 압축돼 보입니다. `gapRatio`는 `gen_tiles.py`가 리그 피치 실측값(110×200mm)으로 계산해 config로 내려보냅니다(T2).

### 6.2 지금 텍스트가 어디 있나: 매 프레임 절대 시각으로 다시 계산

### 6.3 평면 vs 구체

### 8.1 등장방형(360°) 영상에서 폰 한 대의 영역
등장방형 영상은 가로가 경도 0~360°, 세로가 위도 +90~−90°에 그대로 대응하는 지도 같은 그림입니다.
```python
ppd_x = src_w / 360.0          # 경도 1도당 픽셀 (전/후면 모드는 180)
ppd_y = src_h / 180.0          # 위도 1도당 픽셀
d_lat = math.degrees(sh_mm / radius_mm)        # 폰 화면 높이가 구 위에서 차지하는 위도 각도
tile_h = int(round(d_lat * ppd_y)) // 2 * 2    # → 픽셀 높이 (짝수로 - 인코더 요구)

for ri, (lat, count) in enumerate(rows_spec):  # SPHERE_ROWS: (+64.29°, 20대) … (−77.14°, 9대)
    cosl = math.cos(math.radians(lat))
    d_lon = math.degrees(sw_mm / (radius_mm * cosl))   # 같은 폰 폭이라도 극지방일수록 경도 폭이 넓다
    tile_w = int(round(d_lon * ppd_x)) // 2 * 2
    lon_step = 360.0 / count                            # 그 행에서 폰 사이 경도 간격
    for i in range(count):
        lon = (lon_step * i) % 360.0                    # 물리 경도 (번호 규칙: 0°부터 동쪽으로)
        content_lon = (lon + lon_offset) % 360.0        # 설치 회전 보정(22.5°)은 "어디를 자를지"에만
        cx = content_lon * ppd_x                        # 타일 중심 x
        cy = (90.0 - lat) * ppd_y                       # 타일 중심 y
        x, y = round(cx - tile_w / 2), round(cy - tile_h / 2)
        wrap = x < 0 or x + tile_w > src_w              # 0°/360° 경계를 넘는 타일
        meta = {"row": ri, "lat": lat, "lon": lon, "gapRatioX": gap_lon, "gapRatioY": gap_lat, …}
```
- **`1/cos(위도)`**: 지도에서 극지방이 넓게 늘어나 보이는 것과 같은 이유입니다. 같은 크기의 폰이 극지방에서는 더 넓은 경도를 덮습니다.
- **`lon_offset`은 영상만 돌립니다.** `meta.lon`(물리 경도)은 그대로이므로 텍스트 스크롤 같은 다른 기능은 영향을 받지 않습니다(T6).
- 파일 번호(`P001`…)는 위 행부터, 행 안에서는 경도 순으로 매겨지며 CLAUDE.md의 deviceId 규칙과 일치합니다.

```js
  deployRun = { queue, inFlight: new Map(), timers: new Set(), counts: {…}, … };
  immediate.forEach((d, i) => deployTimer(run, () => publishDeviceConfig(d), i * 20));
  pumpDeployRun(run);
}

function pumpDeployRun(run) {
  if (run.inFlight.size >= DEPLOY_MAX_CONCURRENT) return;          // 슬롯 20개가 다 찼으면 대기
  const device = run.queue.shift();
  publishDeviceConfig(device);                                       // wall/device/{id} (retain)
  run.inFlight.set(id, deployTimer(run, () => settleDeployDevice(run, id, 'timeout'), 120000));
  deployTimer(run, () => { run.pumpScheduled = false; pumpDeployRun(run); }, 500);  // 0.5초 뒤 다음 칸
}
// 폰이 wall/ready 또는 wall/error를 보내면 handleFileReady/Error → settleDeployDevice → 슬롯 반환 → pump
```
- **config를 발행하는 것이 곧 "다운로드하라"는 신호**입니다. 폰은 config를 받으면 자기 영상을 `/clips/`에서 받습니다.
- 처음엔 439대에 한꺼번에 발행했다가 Wi-Fi가 포화돼 다운로드 실패와 heartbeat 유실이 났습니다. 발행 간격만 벌리는 방식은 40~50MB 파일에는 소용이 없었습니다. 그래서 **동시에 받는 폰 수 자체를 20대로 제한**했습니다(D9).
- 타이머는 전부 `run.timers`에 모아 둡니다. 새 배포가 오면 `cancelDeployRun`이 한 번에 지웁니다.

```kotlin
private suspend fun process(message: UpdateApk) {
    if (message.versionCode <= BuildConfig.VERSION_CODE) return          // 다운그레이드·같은 버전 무시
    val myStartAt = message.startAt + (deviceId - 1) * message.stepDelayMs   // 순차 점멸과 같은 롤링
    delay(myStartAt - TimeSyncManager.now())
    if (!isSameHost(message.url, readServerIp())) { publishOtaStatus("failed", "URL_HOST_MISMATCH"); return }
    publishOtaStatus("downloading")
    downloadWithRetry(message.url, destFile, message.sha256)            // 재시도 4회 + SHA-256 확인
    publishOtaStatus("installing")
    install(destFile)    // PackageInstaller 세션, USER_ACTION_NOT_REQUIRED (Device Owner면 팝업 없음)
}
```
- 서버는 `wall/ota`에 **retain**으로 발행합니다. 꺼져 있던 폰도 켜지면 받습니다.
- Device Owner가 아니면 설치 결과가 `STATUS_PENDING_USER_ACTION`으로 옵니다. 예전엔 이걸 실패로 처리했고, 지금은 설치 확인 화면을 띄웁니다(M2).

  1. `UpdateReceiver`(`MY_PACKAGE_REPLACED`)가 앱을 다시 띄웁니다.
  2. 다음 실행 때 종료 사유가 `PACKAGE_UPDATED`로 남습니다.
  3. 이 사유는 "의도한 종료(UPDATE)"로 분류되어 재시작 알림에 뜨지 않습니다.
- ⚠ APK 주소는 요청한 호스트로 만들어지므로 `/api/app-deploy`는 반드시 서버 IP로 호출해야 합니다. localhost로 부르면 전부 `URL_HOST_MISMATCH`로 실패합니다.

### 13.2 "사후 보고 + 중복 제거" 패턴 — [server/lib/deviceHealth.js](../../server/lib/deviceHealth.js)
앱이 죽어 있거나 Wi-Fi가 끊긴 동안에는 보고할 수 없습니다. 그래서 폰은 다시 살아난 뒤 **"지난번에 이런 일이 있었다"를 다음 사건이 생길 때까지 heartbeat마다 계속 싣습니다.** 서버는 사건 시각(`at`)으로 중복을 거릅니다.
```js
const exit = msg.lastExit;
if (exit && typeof exit.at === 'number' && !(lastExitAt[id] >= exit.at)) {   // 처음 보는 사건만
  lastExitAt[id] = exit.at;
  store.events.push({ deviceId: id, reason: exit.reason, at: exit.at, … });
  save();                                                                   // data/device-events.json
}
```
- 계속 싣는 이유: 그 순간 서버가 꺼져 있었어도 기록이 유실되지 않게 하기 위해서입니다.
- `lastWifiDrop`도 같은 패턴입니다(`store.wifiDrops`).

## 14. 운영 제어 — 실수와 충돌을 막는 규칙

### 14.1 "지금 무엇이 돌고 있나" — [server.js:1070 `getRunningActivity`](../../server/src/server.js#L1070)
```js
function getRunningActivity() {
  if (state.isPlaying) return 'video';
  if (playlistState.playing) return 'playlist';
  if (textPatternTimer) return 'textPattern';
  if (activity.textScroll) return 'textScroll';
  const now = Date.now();
  if (activity.patternUntil > now) return 'pattern';     // 점멸은 "끝나는 시각"을 기록해 두고 비교
  if (activity.sequenceUntil > now) return 'sequence';
  return null;
}
```
- 이 값이 있으면 모드 변경과 절전이 409로 거부됩니다. 대시보드도 같은 값(`STATUS_UPDATE.running`)으로 버튼을 잠급니다.
- 영상 교체·배포 중이면 재생까지 막습니다(`isDeployBlockingPlay`).

### 14.2 예외: 전부 멈추고 바꾸기 — [server.js:1083 `stopAllActivity`](../../server/src/server.js#L1083)
운영 시간 타이머와 업체 PLAY_TRIGGER에게는 "먼저 정지하세요"라고 안내할 사람이 없습니다. 그래서 돌고 있는 것을 전부 멈춘 뒤 전환합니다.
```js
function stopAllActivity() {
  oneShotReturn.gen += 1;               // "1회 재생 후 복귀" 예약을 무효화(세대 번호)
  if (state.isPlaying) stopVideoPlayback();
  if (playlistState.playing) stopPlaylist();
  if (textPatternTimer) { clearTimeout(textPatternTimer); publishControl({ type: 'TEXT_PATTERN_STOP' }, …); }
  // … 텍스트 스크롤, 점멸, 순차 점멸 정지
}
```

### 14.3 운영 시간 타이머: 경계에서만 — [server.js:2466 `scheduleTick`](../../server/src/server.js#L2466)
```js
function scheduleTick() {                            // 15초마다
  const operating = isOperatingAt(new Date());
  if (operating !== scheduleRuntime.wasOperating) {  // 운영 ↔ 비운영이 "바뀌는 순간"에만
    scheduleRuntime.wasOperating = operating;
    if (operating) scheduleRuntime.pendingStart = true;
    else { stopAllActivity(); enterIdle(); }         // 종료: 절전
  }
  if (scheduleRuntime.pendingStart) {
    if (isDeployBlockingPlay()) return;               // 배포 중이면 끝날 때까지 다음 틱에서 재시도
    scheduleRuntime.pendingStart = false;
    stopAllActivity(); triggerPlay();                 // 시작: 영상 재생
  }
}
```
"18:00에 실행"처럼 예약 타이머를 거는 대신, **주기적으로 판정하고 상태가 바뀔 때만 동작**합니다. 그래서 서버가 재시작되거나 시계가 보정돼도 어긋나지 않고, 운영 중 사람이 한 수동 조작을 덮어쓰지 않습니다.

### 14.4 업체 재생 신호와 1회 재생 후 복귀 — [server.js `/playback-control`](../../server/src/server.js)
```js
if (msg.type === 'PLAY_TRIGGER') {
  if (isDeployBlockingPlay()) return ws.send(ERROR);           // 배포 중
  if (state.idleMode) return ws.send(ERROR);                   // 절전 중
  if (state.schedule.enabled && !isOperatingAt(new Date())) return ws.send(ERROR);   // 운영 시간 밖
  const previousMode = state.currentMode;
  stopAllActivity();
  const startAt = triggerPlay();
  ws.send({ type: 'ACK', received: 'PLAY_TRIGGER', startAt });
  if (previousMode !== 'video') scheduleReturnFromOneShotPlay(previousMode);   // 영상 1바퀴 뒤 원래 모드로
}
```
- 평소 서버는 영상 길이를 몰라도 됩니다. 하지만 1회 재생 후 복귀하려면 1바퀴가 언제 끝나는지 알아야 해서, 이때만 `ffprobe`로 영상 길이를 재서 캐시합니다.
- 그 사이 다른 동작이 끼어들면 `oneShotReturn.gen`(세대 번호)이 바뀌어 복귀하지 않습니다.

## 부록 A. 용어

| 용어 | 뜻 |
|---|---|
| `startAt` | 동작의 기준이 되는 서버 시각(epoch ms). 폰은 `TimeSyncManager.now()`와 비교 |
| offset | 폰 시계와 서버 시계의 차이. `now() = 폰 시각 + offset` |
| drift | 폰 재생 위치 − 있어야 할 위치(ms). +면 앞섬 |
| retain | 브로커가 토픽의 마지막 메시지를 기억했다가 새로 구독한 클라이언트에게 즉시 주는 기능 |
| QoS1 | "적어도 한 번" 전달. 중복 가능 |
| manifest | 배포 기준표. 폰별 영상 파일명·체크섬·위치(meta) |
| tile | 원본 영상에서 폰 한 대 몫으로 자르는 사각형 |
| pitch / gapRatio | 폰 한 칸의 실제 크기(화면 + 간격) / 그중 간격 비율 |
| 등장방형 | 경도·위도를 가로·세로에 그대로 펼친 360° 영상 형식 |
| Device Owner | 기기 관리자 권한. 무인 설치·재부팅·키오스크·홈 고정의 전제 |
| 슬롯 | 배포 때 동시에 다운로드할 수 있는 폰 자리(20개) |
| 사후 보고 | 끊긴 동안 못 보낸 사건을 다시 붙은 뒤 보고(`lastExit`, `lastWifiDrop`) |
