## 4. 핵심 흐름과 리뷰 포인트

### 4.1 재생 동기화
```
/api/play → triggerPlay: MODE_VIDEO 발행 → state.startAt = 지금 → MQTT PLAY{startAt}(retain)
앱: scheduleStart - max(1초, startAt-지금) 대기(최대 5초) → startPlayback - seekTo((지금-startAt) % duration) → play
    (폰마다 메시지 도착 시각이 달라도 "startAt 기준 위치"로 들어가므로 같은 장면에서 시작.
     duration이 아직 없으면 STATE_READY에서 지연 seek)
재생 중: UDP 타임코드(30fps) → DriftCorrector: <16ms 무시, 구간별 속도 ±1.5/3/5%, >200ms seek
TimeSyncManager: /api/time 5회 RTT 중간값, 5초마다
```
**볼 것**
- 시각 계산이 모두 `TimeSyncManager.now()`(서버 시계 환산) 기준인지. 로컬 `System.currentTimeMillis()`를 섞어 쓰는 곳이 없는지
- 루프 경계(영상 끝→처음) 처리: `DriftCorrector`의 목표 위치 점프 감지
- ExoPlayer 호출이 메인 스레드에서만 일어나는지(UDP·MQTT 콜백은 `runOnUiThread`)
- ❓ **검토 요청**: 시간 동기화가 폰당 5초마다 HTTP 5회 → 439대면 서버에 초당 약 440건. 텍스트 모드의 정밀도 때문에 60초에서 5초로 줄인 값(`a7ed9ec`)이라, 영상 모드에서도 이 주기가 필요한지, Wi-Fi 공중 시간 부담이 없는지 의견 필요

### 4.2 영상 배포 (가장 사고가 많았던 영역)
```
서버: manifest 재로드 → 파일이 이미 맞는 폰/오프라인 폰은 20ms 간격으로 바로 발행,
      다운로드가 필요한 폰은 동시 20대 슬롯 (ready/error/120초로 반환) → 끝나면 미완료 폰에만 CHECK_UPDATE
앱:   같은 (파일, 체크섬) 동기화는 하나만 → 임시 파일로 다운로드(재시도 4회) → 체크섬 일치 시에만
      재생 중이면 player.stop → 200ms → rename → 재로드 (NonCancellable) → wall/ready
```
**볼 것**
- `computeFileStatus`(519)가 **매번 현재 manifest와 비교**하는지(예전 버그 `a838842`: 보고 시점 판정을 그대로 돌려줘 슬롯이 무력화됨)
- `deployRun` 취소·교체 시 타이머가 전부 정리되는지(`deployTimer`, `cancelDeployRun`)
- 앱 `requestVideoSync`(1148): 같은 대상이면 무시, 다른 대상이면 이전 작업이 **끝날 때까지 기다린 뒤** 시작하는지. 다운로드 취소가 블로킹 IO를 실제로 끊는지
- 교체 구간(`replaceAndReload`)이 취소되지 않는 구역으로 묶여 config.json·ready 보고가 빠지지 않는지
- 재생 중 파일 교체 경로: 디코더 깨짐(초록 줄무늬)의 원인이었던 경로(`e191745`)가 다시 열리지 않는지

### 4.3 대시보드 영상 교체
```
업로드(multer, 8GB) → gen_tiles.py → deploy.py(hevc_nvenc, -j 10)를 distribute/.staging에
→ 전부 성공하면 promoteStagedDistribute(rename + 실패 시 롤백) → manifest 재로드 → 4.2 배포
취소: 프로세스 트리 종료를 기다린 뒤 임시 폴더·업로드 정리, step='cancelled'
```
**볼 것**
- 실패·취소 때 배포 폴더가 **절대** 반쯤 바뀐 상태로 남지 않는지(`promoteStagedDistribute`의 롤백 경로)
- Windows/Linux 프로세스 종료 차이(`runProcess`, `cancelVideoReplace`의 `cancelKillDone`)
- 자식 프로세스 인자에 사용자 입력(파일명 등)이 셸을 거치지 않는지(`spawn` 배열 인자 사용 여부)
- 업로드 중·교체 중·배포 중 재생·모드 변경·PLAY_TRIGGER·타이머가 모두 막히는지(`blockingWorkLabel` 693, `isDeployBlockingPlay` 687)

### 4.4 패턴·텍스트
- 모든 명령은 미래의 절대 시각을 담고, 폰은 그 시각까지만 기다린 뒤 로컬 애니메이션을 돌립니다. 순차 점멸은 **공통 종료 절대 시각**(`stopAtEpochMs`)을 씁니다(상대 duration 버그 `1134470`).
- 앱의 대기 작업은 `pendingPatternJob` 하나로 통합돼 있습니다(두 개로 나뉘어 취소가 새던 버그 `e9ceded`). 새 대기 작업을 추가할 때 같은 문제가 생기지 않는지 봐 주세요.
- 텍스트 스크롤(`TextScrollView`)은 **매 프레임** 절대 위치를 다시 계산하고, 시계 보정값은 완충합니다(최대 5%씩 추종). 구체는 경도/360°로 가로 위치를 계산하고, `refGapRatioX`를 서버가 하나만 방송합니다.
- 재생목록(1258~): `playlistTimer` 하나로 큐를 넘깁니다. 정지·모드 변경·타이머 경계와 겹칠 때 타이머가 남지 않는지 확인이 필요합니다.

### 4.6 상태 보고·대시보드
- heartbeat 5초 → 서버 1초마다 STATUS_UPDATE(439대분) → 대시보드는 **바뀐 칸만** 다시 그립니다(`applyStatusUpdate`).
- 사후 보고(`lastExit`, `lastWifiDrop`)는 "다음 사건 전까지 계속 싣고 서버가 `at`으로 중복 제거"하는 같은 패턴입니다.
- 볼 것:
  - 구버전 앱(필드 없음)이 섞여도 서버·대시보드가 안전한지
  - STATUS_UPDATE 크기와 1초 주기가 적절한지
  - `device-events.json` 쓰기 빈도(heartbeat마다 쓰지 않는지)

### 4.7 운영 제어 규칙
- **실행 중이면 모드 변경·절전 409**, **교체·배포 중이면 재생·모드 변경·절전 409**. 예외는 운영 시간 타이머와 업체 1회 재생(PLAY_TRIGGER)으로, 실행 중인 것을 전부 정지한 뒤 전환합니다(`stopAllActivity` 1083).
- 1회 재생 후 원래 모드 복귀(`scheduleReturnFromOneShotPlay` 1010)는 그 사이 다른 동작이 끼면 복귀하지 않습니다.
- 타이머(`scheduleTick`, 15초)는 **경계에서만** 동작합니다. 운영 중 수동 조작은 다음 경계까지 유지됩니다.
- 볼 것: 새 API나 버튼을 추가할 때 이 차단 규칙(`rejectWhileReplacing`, `rejectWhileRunning`)을 빠뜨리지 않았는지

## 5. 지켜야 할 불변식

변경 리뷰에서 이 중 하나라도 깨지면 **차단 사유**로 봐 주세요.

1. 여러 폰이 맞춰야 하는 동작은 **서버가 정한 절대 시각(`startAt` 등)을 기준**으로 지시하고, 폰은 그 기준에서 시점·위치를 계산한다. 패턴·텍스트·OTA는 미래 시각을 보내 그때까지 기다리고, 영상은 `startAt`(=발행 시각) 기준 위치로 seek해서 들어간다. "받는 즉시 실행"이나 상대 duration으로 여러 폰을 맞추지 않는다.
2. 폰 시각은 `TimeSyncManager.now()`로만 비교한다.
3. **기기 관리 명령(재시작·재부팅)과 일회성 동작은 non-retain.** retain은 "재접속한 폰이 받아야 하는 최신 상태"(PLAY/STOP/모드, config, OTA, 컬러 상태)에만 쓴다.
4. QoS1이므로 **같은 메시지가 두 번 와도** 결과가 같아야 한다(MODE_VIDEO 중복으로 되감기던 버그, config 중복 재해싱).
5. retain 메시지는 이미 연결된 폰에도 실시간으로 온다. 라이브 명령과 상태 메시지가 서로를 취소하지 않아야 한다(컬러 점멸 버그 `9896947`).
6. 영상 파일은 **체크섬이 맞을 때만** 교체하고, 같은 파일 동기화는 동시에 하나만 돈다.
7. 배포 폴더(`server/distribute`)는 언제나 manifest와 일치하는 완성 상태다(교체는 `.staging`에서).
8. 교체·배포 중에는 재생할 수 없다(외부 트리거·타이머 포함).
9. ExoPlayer와 View는 메인 스레드에서만 다룬다.
10. Device Owner가 아닌 개발 폰에서는 키오스크·홈 고정·생존 알람·Wi-Fi 감시가 **동작하지 않는다**(개발자를 가두지 않음).
11. 같은 APK가 모든 폰에서 돈다. 폰마다 다른 것은 config뿐이다. 새 필드를 넣으면 **옛 APK·옛 서버와 섞여도** 동작해야 한다(필드 없음 = 기존 동작).
12. 안 쓰는 필드는 습관적으로 추가하지 않는다(구체 타일 `col` 미추가 결정 참고).

## 6. 영역별 체크리스트

### 서버 (Node.js)
- [ ] 새 타이머(`setTimeout`/`setInterval`)는 정지·모드 변경·재시작 경로에서 정리되는가
- [ ] 409 차단 규칙(4.7)을 새 API에도 적용했는가
- [ ] 입력 검증: 색상(`HEX_COLOR_RE`), 숫자 범위, `targetDeviceIds`(양의 정수), 시각(`HH:MM`)
- [ ] `server/data/*.json` 저장 실패가 서버를 죽이지 않는가
- [ ] `publishControl`의 retain 여부가 3번 불변식과 맞는가
- [ ] 로그 접두어(`[HTTP] [MQTT] [WS] [UDP]`)와 한국어 주석 컨벤션

### 앱 (Kotlin)
- [ ] MQTT 콜백 → `runOnUiThread`, ExoPlayer는 메인 스레드
- [ ] 코루틴 취소: 블로킹 IO를 실제로 끊는가, 끝나야 하는 구간은 `NonCancellable`인가, 취소 후 임시 파일이 남지 않는가
- [ ] 대기 중인 예약 작업(Job)을 새 명령이 올 때 취소하는가
- [ ] Device Owner 여부에 따라 분기하는가
- [ ] 폐기 예정 API(아래 7장)를 새로 쓰면 Device Owner 예외로 동작하는 근거가 있는가
- [ ] heartbeat에 넣는 값을 읽다가 예외가 나도 heartbeat 자체는 나가는가(`runCatching`)
- [ ] 버전 코드 변경 여부(OTA는 versionCode가 커야 설치됨)

### 대시보드 (app.js)
- [ ] 439칸 전체를 매초 다시 그리지 않는가
- [ ] 사용자 입력을 `innerHTML`로 넣지 않는가(텍스트는 `textContent`)
- [ ] 서버 409 메시지를 토스트로 보여 주는가, 버튼 잠금이 서버 규칙과 일치하는가
- [ ] 도움말(`help.js`)·운영 매뉴얼 문구와 화면 용어가 맞는가

### 파이프라인 (Python)
- [ ] 출력 경로를 절대경로로 확정해 출력하는가(상대경로 사고 이력)
- [ ] Windows cp949 콘솔에서 깨지는 문자(em-dash 등)를 출력하지 않는가
- [ ] 외부 패키지 의존을 추가하지 않았는가
- [ ] 원본 해상도와 tiles.json `source` 크기가 일치하는지 검사하는가

### 9.2 지적 기록 양식

| 항목 | 내용 |
|---|---|
| 위치 | `파일:줄` 또는 함수 |
| 심각도 | **차단**(불변식 위반, 데이터 손상, 현장 장애) / **중요**(조건부 버그, 성능) / **개선**(구조·가독성) / **질문** |
| 상황 | 어떤 입력·순서·타이밍에서 문제가 되는가 |
| 제안 | 고치는 방향(가능하면) |

> 이 프로젝트의 버그는 대부분 **타이밍과 규모**(중복 수신, 동시 다운로드, 재연결 직후, 439대 동시 동작)에서 나왔습니다. "한 대로는 맞는데 439대가 동시에 하면?", "같은 메시지가 두 번 오면?", "이 사이에 다른 명령이 끼면?"을 기본 질문으로 봐 주세요.

- 저장소에서 `/code-review`(현재 변경분) 또는 범위를 지정해 실행하면 됩니다. 이 문서의 5장(불변식)과 7장(위험)을 함께 주면 프로젝트 특성에 맞는 지적이 나옵니다.
