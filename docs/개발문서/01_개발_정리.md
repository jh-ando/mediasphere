## 1. 프로젝트 개요

| 항목 | 내용 |
|---|---|
| 목적 | 지름 1.8m 구체 표면에 Galaxy A15 **439대**를 붙여 하나의 360도 영상/패턴/텍스트를 정밀 동기화 재생하는 미디어 설치물 |
| 고객 요구 | 영상 분할 재생, 화면 점멸 패턴, 스트레스 컬러 오버레이(키오스크 → 폐기), 구체 표면을 흐르는 텍스트, 폰을 픽셀로 쓰는 텍스트 표시, 외부 업체 재생 신호 연동, 운영 시간 자동화 |
| 동기화 목표 | 재생 시작 오차 < 16ms, 드리프트 < 50ms (보정: 속도 조절 / 200ms 초과 시 seek) |
| 구성 | 마스터 서버(Node.js 20, Ubuntu 24.04) + Android 앱(Kotlin, ExoPlayer Media3, Paho MQTT) + 영상 분할 파이프라인(Python 3.11, FFmpeg) + Mosquitto 브로커 |
| 네트워크 | 5GHz 전용 폐쇄망, AP 여러 대에 연속 블록으로 폰 배정 |
| 규모 변화 | 1대 → 16대 → 15대 분할 시연 → 100대(20열×5행 평면) → 439대 구체 |

### 1.1 시스템 구조

```
            ┌──────────── 마스터 서버 (Node.js) ────────────┐
 대시보드 ◀─┤ WebSocket :3000   HTTP :3000 (/api, /clips, /apk)│
 (브라우저)  │ UDP 멀티캐스트 239.0.0.1:5000 (타임코드 30fps)   │
 외부 업체 ─▶│ WebSocket /playback-control (PLAY_TRIGGER)      │
            │ 영상 교체: 업로드 → gen_tiles → ffmpeg 인코딩 → 배포│
            └──────┬──────────────────────────────┬──────────┘
                   │ MQTT (Mosquitto :1883)        │ UDP 타임코드
                   ▼                               ▼
     ┌────────── Galaxy A15 × 439 (같은 APK, config.json만 다름) ──────────┐
     │ 영상 모드: ExoPlayer + DriftCorrector(타임코드 기준 속도/seek 보정)   │
     │ 패턴 모드: PatternView 점멸/순차 점멸/재생목록/텍스트 패턴             │
     │ 텍스트 모드: TextScrollView (파라미터만 받아 자기 몫을 로컬 렌더링)     │
     │ 공통: TimeSyncManager(/api/time), heartbeat 5초, 파일 동기화, OTA,    │
     │       Device Owner(무인 설치·재부팅·키오스크 잠금·홈 고정)              │
     └────────────────────────────────────────────────────────────────────┘
```

**MQTT 토픽**: `wall/control`(전체 명령), `wall/device/{id}`(폰별 config, retain), `wall/pattern/{id}`(텍스트 패턴 셀), `wall/status/{id}`(heartbeat), `wall/ready|error/{id}`(파일 검증 결과), `wall/ota`·`wall/ota/status/{id}`, `wall/state/color`.
세부 프로토콜·API는 [CLAUDE.md](../../CLAUDE.md)와 `docs/LGU_*_Protocol.md` 참고.

## 3. 이슈와 해결

형식: **증상** → 원인 → 해결 (`커밋`). ★는 다시 생기기 쉽거나 비슷한 프로젝트에서 반복될 가능성이 큰 항목입니다.

### 3.1 성능 (Phase 0)

| # | 증상 | 원인 | 해결 |
|---|---|---|---|
| P1 | 모니터링을 꺼도 CPU 60% 이상 | 디코딩은 하드웨어(`c2.mtk.avc.decoder`)로 정상이었음. 비용은 ExoPlayer 렌더 스케줄링, MediaCodec 콜백, SurfaceFlinger IPC에서 나옴. **초당 픽셀 처리량(해상도×fps)에 비례** | 480×854@30fps ≈ 40%, 720p30 ≈ 50%, 720p60/1080p30 ≈ 60~65%를 측정한 뒤 **480p30 채택** |
| P2 | 터널링 모드를 켜면 오히려 CPU 70% | 이 기기의 SurfaceView 버퍼 큐와 맞지 않음(`BLASTBufferQueue` 오류) | 원복. 터널링은 쓰지 않음 |
| P3 | `findstr`로 logcat을 거르면 아무것도 안 나옴 | Windows 파이프 버퍼링. 디코더 로그는 재생을 시작할 때만 한 번 찍힘 | 필터 없이 보거나 재생을 다시 시작해서 확인 |

### 3.2 동기화 / 타임코드 ★

| # | 증상 | 원인 | 해결 |
|---|---|---|---|
| S1 | ping은 되는데 UDP 멀티캐스트가 수신되지 않음 | Android는 `WifiManager.MulticastLock` 없이 멀티캐스트 패킷을 버림 | MulticastLock을 획득하고 소켓 생성·가입·수신 단계마다 로그를 남김 |
| S2 | `/api/stop`을 보내도 폰이 멈추지 않음 | 서버가 정지 중에는 타임코드를 아예 보내지 않아서 정지 신호가 전달될 길이 없었음 | 패킷을 항상 보내고 `isPlaying` 필드 추가(임시). Phase 2에서 MQTT PLAY/STOP으로 이전 |
| S3 | drift가 한쪽으로 계속 치우침 | 폰 시계와 서버 시계가 서로 다름 | **TimeSyncManager**: `/api/time`을 5회 호출해 RTT 중간값으로 오프셋 계산, 이후 `now() = 로컬 + offset` |
| S4 | drift가 수렴하는 데 약 3분 걸림 | ±2% 고정 속도 보정 | 구간별 비례 보정: 16~50ms ±1.5%, ~100ms ±3%, ~200ms ±5%, 그 이상은 seek |
| S5 | 루프 경계에서 drift가 +6000ms로 튐 | 영상이 처음으로 돌아가는 순간 목표 위치가 끝에서 처음으로 점프 | 이전 대비 목표 위치 변화가 영상 길이의 50%를 넘으면 그 프레임은 보정 생략 |
| S6 | 시작 직후 drift가 -100~+200ms | 패킷 도착 지연과 서버 기준이 아닌 로컬 시각 사용 | 시작 신호 후 1초 대기, `play()` 직전에 `TimeSync.now() - startAt`으로 계산한 위치로 `seekTo` |
| S7 | 시간이 지나면 싱크가 무작위로 틀어짐 | 시계 오프셋이 시작 시 1회만 측정됨. 정상 범위로 돌아와도 재생 속도가 1.0으로 복원되지 않음 | 1분마다 재동기화(텍스트 도입 후 5초), `ACTION_TIME_CHANGED`에서 즉시 재동기화, 정상 범위에서 속도 1.0 복원. Android 13+의 `registerReceiver` 플래그 누락으로 생길 크래시는 구현 단계에서 미리 차단 |
| S8 | 텍스트 스크롤이 재동기화 순간마다 한 번씩 튐 | 매 프레임 `now()`를 그대로 쓰므로 오프셋이 바뀌면 위치가 순간 이동 | `smoothedOffsetMs`로 완충(최대 5%씩 추종, 500ms 이상 변화만 즉시 반영) (`a7ed9ec`) |
| S9 | **특정 폰 1대만** 텍스트가 앞서 지나감. 재동기화 주기를 바꿔도 효과 없음 | 그 폰의 시스템 시계가 몇 달 틀려 있었음(로그 날짜 05-24, 다른 폰은 08-14) | 기기 교체. 교훈: 같은 APK/config인데 한 대만 다르면 **기기 시계와 설정부터** 확인 |
| S10 | 서버 전원 모드가 '밸런스'면 동기화 이탈 | 타임코드 송출이 지연됨 | 서버는 '퍼포먼스' 모드로 고정 (운영 주의사항) |

**설계 원칙으로 정착한 것**: 모든 명령은 "지금"이 아니라 **미래의 절대 시각(`startAt`)**을 담아 보내고, 폰은 `TimeSyncManager.now()`로 그 시각까지 기다립니다. 긴 애니메이션(텍스트 스크롤)은 매 프레임 절대 위치를 다시 계산하고, 짧은 애니메이션(점멸·텍스트 패턴)은 시작/종료 절대 시각만 맞춘 뒤 로컬로 진행합니다.

### 3.4 파이프라인 / 배포 ★

## 7. 교훈

1. **성능부터 실측했다.** Phase 0에서 해상도별 CPU를 재고 480p로 정한 덕분에 이후 439대까지 같은 전제가 유지됐다.
2. **시간은 서버 기준 절대 시각으로 다룬다.** 상대 시간(duration, "지금")을 쓴 곳마다 버그가 났다(A6, S6).
3. **MQTT 의미를 정확히 안다.** retain은 "새 구독자에게도"이지 "기존 구독자에게 안 감"이 아니다(A5). QoS1은 중복 수신을 전제로 한다(A9, D8). Paho 자동 재연결은 첫 연결 이후에만 동작한다(M5).
4. **규모가 커지면 새 버그가 생긴다.** 16→100→439대마다 다운로드 폭주, 균일 격자 가정 붕괴, 상태 판정 오류가 새로 드러났다. 시뮬레이터로 N대를 흉내 내는 테스트가 필수다.
5. **"한 대만 이상"은 대개 기기 문제다.** 시계, 설정, 하드웨어부터 의심한다(S9).
6. **가설이 틀리면 빨리 버린다.** 전체화면(A4)과 텍스트 싱크(S9) 모두 첫 가설에 3번 이상 매달렸다. 효과가 없다는 것 자체가 단서다.
7. **현장 접근이 어려운 설치물은 원격 복구 수단을 처음부터 설계한다**(원격 재시작/재부팅, 자동 실행, 종료 사유 보고).
8. **운영자 관점의 잠금과 안내**(실행 중 변경 차단, 도움말)가 기능만큼 중요하다.
