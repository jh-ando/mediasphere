# 실시간 프레임 전송 프로토콜 명세 (외주사 전달용)

버전: draft v0.1 (2026-08-05)
대상: 태블릿 앱 → MediaSphere 서버 실시간 픽셀 프레임 전송 연동

## 0. 확정된 값 (2026-08-05)

| 항목 | 값 |
|---|---|
| 서버 HTTP 포트 | `3000` |
| 전체 디바이스 수 (deviceId 범위) | `1 ~ 439` |

## 1. 시스템 개요

```
태블릿 앱 ──HTTP POST──▶ MediaSphere 서버 ──MQTT 발행──▶ 안드로이드 폰 (개별)
           /api/frame                      wall/frame/{deviceId}
```

- **용도**: 실시간 인터랙션 효과(예: 터치에 반응하는 물결 등). 정밀 이미지/텍스트 표시 목적이 아니므로, 폰 간 프레임 완전 동기화보다 **반응 지연 최소화**가 우선순위다.
- 태블릿 앱은 폰 1대당 `84×182px` 픽셀 배열을 실시간 생성한다.
- 태블릿 앱은 생성된 배열을 **디바이스 1대분씩** HTTP POST로 서버에 전송한다 (배치 전송 아님, 디바이스별 개별 요청).
  - 배치로 묶지 않는 이유: (1) 배치는 439대 전체 계산이 끝날 때까지 기다렸다 한 번에 보내야 해서, 계산이 먼저 끝난 디바이스도 늦게 반영됨 — 실시간 인터랙션 목적에 역행. (2) 서버(Node.js)는 싱글 스레드라, 배치 하나(~65MB 추정)를 파싱하는 동안 이벤트 루프가 블로킹되면 그 순간 전체 인터랙션 반응이 함께 지연됨. (3) 결국 MQTT 발행은 `wall/frame/{deviceId}`로 디바이스별로 나가야 하므로, 배치는 HTTP 요청 횟수만 줄일 뿐 서버의 최종 fan-out 비용은 그대로 남음.
- 서버는 `deviceId` 기준으로 해당 폰의 MQTT 토픽에 그대로 라우팅(fan-out)한다.
- 서버·폰 간 기존 통신(MQTT `wall/control`, UDP 타임코드)과 독립적으로 동작하며, 이 프레임 데이터는 영상 재생/패턴 모드와 별개의 실시간 오버레이 채널이다.

## 2. HTTP POST 엔드포인트

```
POST http://192.168.8.10:3000/api/frame
Content-Type: application/json
```

### 요청 바디

```json
{
  "deviceId": 17,
  "width": 84,
  "height": 182,
  "format": "RGB888",
  "seq": 10234,
  "pixels": [255, 0, 0, 255, 0, 0, ...]
}
```

| 필드 | 타입 | 설명 |
|---|---|---|
| `deviceId` | integer | 대상 폰의 deviceId. [3. deviceId 규칙](#3-deviceid-규칙) 참조 |
| `width` | integer | 고정값 `84` |
| `height` | integer | 고정값 `182` |
| `format` | string | 고정값 `"RGB888"` (픽셀당 R,G,B 3바이트, 알파 없음) |
| `seq` | integer | 태블릿 앱이 증가시키는 프레임 시퀀스 번호. 서버/폰이 오래된 프레임을 버리는 데 사용 (권장) |
| `pixels` | integer[] | 길이 `width * height * 3 = 45864`. row-major, 좌상단 원점, `[R,G,B,R,G,B,...]` 순서. 각 값 0~255 |

`startAt` 같은 절대 시각 스케줄링 필드는 넣지 않는다 — 이 채널은 기존 `COLOR_CHANGE`/`PATTERN_START`처럼 예약 발행이 아니라, 도착 즉시 적용하는 실시간 스트림이다.

### 응답

성공: `200 OK`, 바디 없음.
- `deviceId`/`seq`를 되돌려줄 필요 없음 — 요청·응답은 같은 HTTP 연결로 1:1 매칭되므로 태블릿이 이미 아는 값을 다시 실어 보내는 건 서버 쪽 JSON 생성 비용만 늘릴 뿐(10fps × 최대 439대 = 초당 최대 4,390건 규모).

실패 (예: deviceId 범위 밖, pixels 길이 불일치, width/height 불일치): `400`
```json
{ "ok": false, "error": "pixels 길이는 45864여야 합니다 (받은 값: 12000)" }
```

- **태블릿 앱은 응답을 기다리지 않고 다음 프레임을 바로 전송해야 한다 (non-blocking).** 요청-응답을 동기적으로 기다리면 왕복 지연이 그대로 실효 fps에 더해져 10fps 목표가 무너진다. 실패 응답은 디버깅/로그용으로만 사용하고, 다음 프레임 전송을 막는 조건으로 쓰지 않는다.

## 3. deviceId 규칙

- `/sdcard/mediasphere/config.json`의 `"deviceId"` 필드와 동일한 정수 체계를 그대로 사용한다.
- 0 패딩 없는 순수 정수 (`1`, `17`, `439` 등 — `"017"` 아님).
- 유효 범위: `1 ~ 439`.
- 범위 밖 deviceId 또는 현재 offline인 deviceId로 요청이 오면 서버는 `400`을 반환하거나(권장) 조용히 무시한다 — 정책은 구현 단계에서 결정.

## 4. MQTT 토픽 구조 및 페이로드

```
토픽: wall/frame/{deviceId}
방향: 서버 → 개별 폰
QoS: 0
retain: false
```

```json
{
  "type": "FRAME",
  "width": 84,
  "height": 182,
  "format": "RGB888",
  "seq": 10234,
  "pixels": [255, 0, 0, 255, 0, 0, ...]
}
```

- HTTP 요청 바디의 `deviceId`를 제외한 나머지 필드를 그대로 실어 해당 `deviceId` 전용 토픽에 발행한다.
- **retain을 쓰지 않는다** — 프레임은 초당 10장씩 계속 갱신되는 실시간 데이터이므로, 새로 접속한 폰에 오래된 프레임이 남아있을 이유가 없다 (heartbeat와 동일한 성격).
- **QoS 0을 쓴다** — `wall/control`(QoS1, 명령 유실 방지)과 달리, 프레임은 한두 장 유실돼도 다음 프레임이 바로 이어지므로 재전송 오버헤드가 오히려 손해다.
- 이 토픽은 현재 안드로이드 앱이 구독하고 있지 않다. **폰 쪽 구독 추가는 자사 Android 팀 작업이며 외주사 범위가 아니다.**

## 5. 제약사항

### fps
- 목표 10fps (100ms 간격).
- 태블릿 앱은 이전 프레임에 대한 서버 응답을 기다리지 않고 다음 프레임을 보내지 않는다 (요청 큐잉 금지, 최신 프레임만 유효).

### 데이터량 (⚠️ 설계 검토 필요)

디바이스 1대, 1프레임 기준:
- raw 픽셀: `84 × 182 × 3 byte = 45,864 byte (~44.8 KB)`
- 이걸 JSON 정수 배열로 표현하면 텍스트 인코딩 오버헤드 때문에 **실제 페이로드는 raw보다 3배 이상 커진다** (콤마·자릿수 포함 시 프레임당 약 150~160 KB로 추정).

10fps 기준 초당 트래픽 (JSON 배열 방식):
| 동시 대수 | 초당 트래픽 (추정) |
|---|---|
| 15대 (현재 테스트) | 약 2.3 MB/s |
| 100대 | 약 15.6 MB/s |
| 439대 (최종) | 약 68 MB/s |

이 수치는 **HTTP 수신(태블릿→서버) + MQTT 발행(서버→폰) 양쪽에 각각 발생**하므로 서버 NIC/CPU와 폐쇄 5GHz Wi-Fi 대역폭에 상당한 부담이 될 수 있다. 439대 풀스케일에서는 특히 위험 수준.

권장 검토 사항 (개발 착수 전 결정 필요, 본 문서 범위 밖):
1. `pixels`를 정수 배열 대신 **Base64 인코딩된 바이너리**로 전송 (raw 대비 약 1.33배로, 정수배열 대비 훨씬 작음).
2. 아예 HTTP/MQTT 바디를 JSON이 아닌 **바이너리(raw bytes)**로 전송하고 헤더로만 메타데이터(deviceId, seq) 전달.
3. 439대 전체가 아니라 실제 화면에 나타나는 영역의 디바이스만 갱신 (변화 없는 폰은 프레임 재전송 생략).
4. 10fps를 낮추거나, 저해상도/인덱스 컬러 팔레트로 프레임 자체를 줄이는 방안.

본 문서는 사용자 요청대로 "raw RGB 배열, 10fps" 기준으로 작성했으나, 위 트래픽 추정치를 근거로 **외주 개발 착수 전에 반드시 내부적으로 재검토**할 것을 권장한다.

### 기타
- `width`/`height`는 현재 고정값(`84×182`)이지만 향후 해상도가 바뀔 수 있으므로 필드 자체는 유지한다 (하드코딩 금지, 매 요청마다 검증).
- 서버는 `deviceId`가 offline 상태여도 MQTT 발행 자체는 시도한다 (heartbeat 타임아웃과 프레임 전송은 별개 판단 기준).
